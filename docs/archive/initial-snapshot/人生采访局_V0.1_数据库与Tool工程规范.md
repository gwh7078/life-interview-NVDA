# 人生采访局 V0.1｜数据库与 Agent Tool 工程规范

**用途**：交给另一个 AI / Codex 直接进行后端、数据库和 Agent Tool 开发。  
**版本**：V0.1（比赛原型）

## 0. 已确认的核心架构决策

1. V0.1 采用“一名注册用户 = 一份人生档案”，因此用户账户与人生档案合并为一张 `users` 表。
2. 数据库保持精简，共 7 张核心表：`users`、`life_stages`、`stories`、`interview_sessions`、`transcript_segments`、`story_candidates`、`memoir_documents`。
3. Agent Tool **不与数据库表一一对应**。实时 Agent 使用“场景级聚合 Tool”，一次调用拿齐当前场景所需上下文，避免连续多轮 Tool Call 带来的延迟。
4. `story_interview` 是纯 Question Skill：**只读，不允许写 Story State、Story、用户档案或候选故事**。采访过程中只由后端持续保存 Transcript。
5. 访谈结束后，由 `session_closeout` 读取完整本次 Transcript + 旧 Story State，判断哪些内容应写入结构化记忆，并通过一次批量写入 Tool 提交。
6. `stories.story_state_json` 保存当前 Story State。V0.1 暂不单独建立 Story State 版本表；修改前/修改后状态保存在 `interview_sessions.closeout_result_json`，满足调试与回滚需要。
7. Transcript 是原始证据，不应被 AI 覆盖或改写；Story State 是 AI 的结构化工作记忆；成文结果另存 `memoir_documents`。

## 1. 数据关系

```text
users
 ├─ life_stages
 │    └─ stories
 │
 ├─ interview_sessions
 │    └─ transcript_segments
 │
 ├─ story_candidates
 └─ memoir_documents
```

## 3. Agent Tool 的总原则

### 3.1 不要按数据库表暴露 CRUD

错误方式：

```text
get_user → get_stage → list_stories → get_story → get_story_state ...
```

正确方式：

```text
get_story_interview_context(story_id)
```

由后端内部使用 SQL JOIN、并行查询或缓存一次拼装完整上下文。

### 3.2 Tool 分两层

**Agent-facing Tool**：按业务场景设计，数量少，供 LLM 调用。  
**Backend Internal Service**：负责 CRUD、Session、Transcript、事务等，不暴露给 LLM。

### 3.3 实时 Agent 的性能目标

- 进入一个场景时，原则上只做 1 次聚合上下文调用。
- 连续访谈过程中原则上 0 次数据库调用。
- 只有 AI 明确需要核对历史原话时才调用 Transcript Search。
- 写入操作尽量一次 Tool 完成，并在数据库事务中执行。

## 4. Agent-facing Tool 完整定义

### T01 get_onboarding_context

**用途**：首次建档开始或继续时，一次获取已有用户资料、已有人生阶段、已有故事、尚未处理候选故事等，供 `onboarding_builder` 判断还缺什么、是否达到生成人生阶段/故事的条件。

输入：
```json
{"user_id":"uuid"}
```

输出：
```json
{
  "user": {"name":"","birth_date":"","profile_summary":"","onboarding_status":""},
  "life_stages": [{"stage_id":"","title":"","start_date":"","end_date":"","summary":""}],
  "stories": [{"story_id":"","stage_id":"","title":"","short_summary":"","status":""}],
  "pending_story_candidates": []
}
```

### T02 apply_onboarding_result

**用途**：将 Onboarding Skill 最终确认的资料一次批量写入。可同时更新用户信息、创建/修改人生阶段、创建正式故事或候选故事。

输入：
```json
{
  "user_id":"uuid",
  "source_session_id":"uuid",
  "profile_patch":{},
  "stages_to_create":[],
  "stages_to_update":[],
  "stories_to_create":[],
  "candidates_to_create":[],
  "onboarding_completed":true
}
```

输出：
```json
{
  "success":true,
  "created_stage_ids":[],
  "created_story_ids":[],
  "created_candidate_ids":[]
}
```

规则：后端事务执行；部分失败时整体回滚。

### T03 get_life_stage_editor_context

**用途**：新增/修改人生阶段时，一次返回人物摘要、全部阶段轮廓、目标阶段详情以及该阶段下 Story 名称与一句话简介。

输入：
```json
{"user_id":"uuid","stage_id":"optional_uuid"}
```

输出：
```json
{
  "profile_summary":"",
  "all_stages":[{"stage_id":"","title":"","start_date":"","end_date":"","summary":"","sort_order":1}],
  "target_stage":{"stage_id":"","title":"","start_date":"","end_date":"","summary":""},
  "stage_stories":[{"story_id":"","title":"","short_summary":"","status":""}]
}
```

### T04 apply_life_stage_changes

**用途**：一次提交人生阶段相关修改，避免 Agent 连续调用多个 CRUD。

输入：
```json
{
  "user_id":"uuid",
  "source_session_id":"optional_uuid",
  "stages_to_create":[],
  "stages_to_update":[],
  "stage_order":[],
  "stories_to_move":[],
  "candidates_to_create":[]
}
```

输出：
```json
{"success":true,"created_stage_ids":[],"updated_stage_ids":[]}
```

### T05 get_story_interview_context

**用途**：进入单个 Story 的 Question Mode 时，一次性拿齐绝大多数需要的上下文。

输入：
```json
{"user_id":"uuid","story_id":"uuid"}
```

输出：
```json
{
  "user":{"name":"","nickname":"","profile_summary":""},
  "life_stage":{"stage_id":"","title":"","start_date":"","end_date":"","summary":""},
  "story":{
    "story_id":"",
    "title":"",
    "short_summary":"",
    "story_state":{},
    "completeness":0,
    "status":""
  },
  "sibling_stories":[{"story_id":"","title":"","short_summary":"","status":""}]
}
```

权限：只读。该 Skill 不获得任何 Story/Profile/Stage 写入 Tool。

### T06 search_transcript

**用途**：只有当实时 Agent 或其他 Skill 需要核对历史原话、时间、人物、矛盾等时才调用。

输入：
```json
{
  "user_id":"uuid",
  "query":"检索内容",
  "story_id":"optional_uuid",
  "stage_id":"optional_uuid",
  "limit":8
}
```

输出：
```json
{
  "matches":[
    {"segment_id":"","session_id":"","story_id":"","speaker":"user","text":"","score":0.91}
  ]
}
```

底层可以先用全文检索；未来换 embedding/hybrid search 时 Tool 接口不变。

### T07 get_transcript_context

**用途**：根据搜索命中的片段，再取前后若干句话，避免把整段历史 Transcript 塞给 Agent。

输入：
```json
{"segment_ids":["uuid"],"context_before":2,"context_after":2}
```

输出：
```json
{
  "segments":[{"segment_id":"","session_id":"","sequence_number":1,"speaker":"user","text":""}]
}
```

### T08 get_session_closeout_context

**用途**：访谈结束后，一次拿齐 Closeout Skill 需要的全部输入。

输入：
```json
{"session_id":"uuid"}
```

输出：
```json
{
  "session":{"session_id":"","session_type":"story","started_at":"","ended_at":""},
  "user":{"user_id":"","profile_summary":"","occupation_summary":"","family_summary":""},
  "life_stage":{"stage_id":"","title":"","summary":""},
  "story":{"story_id":"","title":"","short_summary":"","story_state":{},"completeness":0,"status":""},
  "transcript":[{"segment_id":"","sequence_number":1,"speaker":"user","text":""}],
  "existing_story_candidates":[]
}
```

### T09 apply_session_closeout

**用途**：Closeout Skill 完成判断后，一次性提交所有结构化更新。

输入：
```json
{
  "session_id":"uuid",
  "story_id":"uuid",
  "new_story_state":{},
  "story_patch":{"short_summary":"","completeness":75,"status":"interviewing"},
  "profile_patch":{},
  "new_story_candidates":[],
  "session_summary":"",
  "changes":[],
  "conflicts":[],
  "model_name":"",
  "skill_version":""
}
```

输出：
```json
{
  "success":true,
  "story_updated":true,
  "created_candidate_ids":[],
  "session_status":"completed"
}
```

实现要求：
- 后端读取当前 Story State 并自动保存为 `previous_story_state`。
- 写入 `new_story_state` 后，将前后状态及 changes/conflicts 等一起保存到 `interview_sessions.closeout_result_json`。
- 全过程数据库事务执行。
- `story_interview` 无权调用此 Tool。

### T10 get_archive_organizer_context

**用途**：全局档案整理时一次返回全部人生阶段轮廓、Story 轮廓及待处理 Story Candidate。默认不返回所有 Story State 与 Transcript，避免上下文爆炸。

输入：
```json
{"user_id":"uuid"}
```

输出：
```json
{
  "profile_summary":"",
  "life_stages":[],
  "stories":[{"story_id":"","stage_id":"","title":"","short_summary":"","status":"","completeness":0}],
  "pending_story_candidates":[]
}
```

如需细查单个故事，可复用 `get_story_interview_context` 与 Transcript Tool。

### T11 apply_archive_changes

**用途**：对已经确认的全局整理建议进行批量写入，例如移动 Story、修改阶段、正式创建 Candidate 对应 Story。

输入：
```json
{
  "user_id":"uuid",
  "stages_to_update":[],
  "stories_to_update":[],
  "stories_to_move":[],
  "candidates_to_resolve":[]
}
```

输出：
```json
{"success":true,"changed_items":[]}
```

V0.1 约束：自动 merge、split、delete 默认不实现；可以让 Skill 输出建议，由用户确认后再执行。

### T12 get_memoir_context

**用途**：为成文 Skill 一次准备指定 Story、Life Stage 或整本人生成文所需的结构化资料。

输入：
```json
{"user_id":"uuid","scope_type":"story","scope_id":"uuid"}
```

输出：
```json
{
  "user":{"name":"","profile_summary":""},
  "scope":{"type":"story","title":""},
  "life_stage":{},
  "stories":[{"story_id":"","title":"","story_state":{},"short_summary":""}],
  "existing_documents":[]
}
```

需要用户原话时，Memoir Skill 再按需调用 `search_transcript` / `get_transcript_context`。

### T13 save_memoir_document

**用途**：保存新文稿或新版本。

输入：
```json
{
  "user_id":"uuid",
  "scope_type":"story",
  "scope_id":"uuid",
  "title":"",
  "content":"",
  "source_json":{},
  "status":"draft"
}
```

输出：
```json
{"success":true,"document_id":"uuid","version_number":1}
```

## 5. 不暴露给 LLM 的 Backend Internal Service

以下能力属于应用后端，不应该作为 Agent Tool：

- `create_interview_session(...)`：用户进入采访页面时由 Backend 创建 Session。
- `append_transcript_segment(...)`：语音/文字对话过程中自动追加 Transcript。
- `end_interview_session(...)`：用户点击结束时写入 `ended_at` 并把状态改为 `ended`。
- `set_session_processing/completed/failed(...)`：Closeout 工作流状态维护。
- 用户鉴权、user_id 解析、音频上传、ASR/TTS、数据库连接与事务管理。

原因：这些动作不需要 AI 判断，放进 LLM Tool 只会增加延迟和出错面。

## 6. Skill 与 Tool 权限矩阵

| Skill | 模式 | 允许 Tool | 写权限 |
|---|---|---|---|
| onboarding_builder | Question | T01、T02 | 可批量写 Profile / Stage / Story / Candidate |
| life_stage_editor | Question | T03、T04 | 只写阶段相关结构 |
| story_interview | Question | T05、T06、T07 | **无业务数据写权限** |
| session_closeout | Background | T08、T09，必要时 T06/T07 | Story State 的核心写入者 |
| archive_organizer | Background/Review | T10、T11，必要时 T05/T06/T07 | 经确认后批量整理 |
| memoir_writer | Generation | T12、T13，必要时 T06/T07 | 只写 memoir_documents |

## 7. 核心数据流

### 7.1 单个 Story 采访

```text
用户进入故事
  ↓
Backend 创建 interview_session
  ↓
story_interview 调 T05 get_story_interview_context（一次）
  ↓
Agent 持续 Question
  ↓
每一句对话由 Backend 自动 append transcript
  ↓
只有需要核对历史资料时才调用 T06/T07
  ↓
采访过程中 Story State 完全不写
```

### 7.2 通话结束

```text
用户点击结束
  ↓
Backend end_session
  ↓
session_closeout 调 T08（一次取齐）
  ↓
LLM 判断：
新增事实 / 补充 / 纠正 / 人物 / 地点 / 时间
开放问题 / 信息冲突 / 新故事线索
  ↓
生成完整 new_story_state
  ↓
T09 apply_session_closeout（一次事务写入）
  ↓
stories 更新当前 State
story_candidates 新增线索
interview_sessions 保存前后差异与摘要
Session = completed
```

### 7.3 首次建档

```text
T01 一次读取当前已有信息
  ↓
Question Mode 补齐关键资料
  ↓
AI 判断是否达到建立人生时间轴条件
  ↓
AI 提取人生阶段
  ↓
在阶段之后提取明确 Story / Candidate
  ↓
T02 一次批量落库
```

## 8. 数据库索引建议

最少创建以下索引：

- `life_stages(user_id, sort_order)`
- `stories(user_id, stage_id, status)`
- `interview_sessions(user_id, story_id, created_at)`
- `transcript_segments(session_id, sequence_number)` 唯一或联合索引
- `story_candidates(user_id, status)`
- `memoir_documents(user_id, scope_type, scope_id, version_number)`

Transcript 搜索 V0.1 可以先使用数据库全文索引；未来如果接向量检索，不改变 T06 的外部接口。

## 9. V0.1 明确不做

- 一个账户管理多个人生档案。
- 独立 `story_state_versions` 表。
- 复杂长期 Memory / 全局自动 RAG。
- Agent 自由访问数据库 CRUD。
- Story Interview 边聊边写 Story State。
- 自动删除、自动合并、自动拆分重要人生数据。

这些未来需要时再升级，不应阻塞比赛原型。

## 10. 推荐开发顺序

1. 建立 7 张数据库表、枚举、索引和测试数据。
2. 完成 Backend Internal Service：Session 创建/结束、Transcript 自动追加。
3. 优先开发 T05 `get_story_interview_context`，跑通纯文字 Story Interview。
4. 开发 T08 + T09，跑通“结束访谈 → Closeout → Story State 更新”的完整闭环。
5. 开发 T06/T07 Transcript Search，解决历史事实核对。
6. 开发 Onboarding 的 T01/T02。
7. 开发 Life Stage 的 T03/T04。
8. 开发 Memoir 的 T12/T13。
9. 最后补 Archive Organizer 的 T10/T11。

**第一条真正应验收的 Vertical Slice：**

```text
打开 Story
→ 一次加载上下文
→ 多轮文字采访
→ Transcript 自动保存
→ 用户结束
→ Closeout 分析
→ Story State 更新
→ 新 Story Candidate 被识别
→ 再次打开 Story 时能读到新的 State
```

只要这条链路稳定，Web App、语音和 NemoClaw 都可以在此基础上继续接入。

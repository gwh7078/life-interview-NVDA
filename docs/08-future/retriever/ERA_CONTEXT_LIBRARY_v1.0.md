# 时代背景检索库设计 v1.0

> Status: **Future / Planned / Deferred**
>
> Date: 2026-09-20
>
> 当前版本不开发、不计入已实现能力。本文件只冻结未来产品与技术方向。
>
> 目标：为未来 Realtime Slow System 提供与受访者所处年代相关的社会、时事、娱乐、体育、科技、消费与日常生活背景，帮助采访官自然唤起记忆、寻找话题，但绝不把外部时代背景自动写成用户个人事实。

## 1. 为什么需要时代背景检索

人生访谈不仅需要“记得用户过去说过什么”，还需要理解：

> **用户生活在什么时代。**

例如用户说：

> “我 2001 年大学毕业，后来去了北京。”

个人历史召回只能提供用户自己的既有信息。

未来时代背景检索可以补充与该时间、地点、年龄和人生阶段相关的候选话题，例如：

- 2001 年北京申奥成功；
- 当时网吧、QQ、门户网站快速普及；
- 当年的热门音乐、电视剧、体育赛事；
- 当时大学毕业生常见的就业与城市生活背景。

这些内容不是用户事实，只是采访线索。

## 2. 与慢系统的关系

未来慢系统可以拥有三类独立检索能力：

```text
Realtime Slow System
├─ 个人历史召回
│  └─ 以前采访里说过什么
│
├─ 个人历史事实检索
│  └─ 人物 / 年份 / 地点 / 工作 / 家庭关系等
│
└─ 时代背景检索
   └─ 当年发生过什么、流行什么、社会在讨论什么
```

三者目的不同：

- 个人历史召回：保持长期采访连续性；
- 个人历史事实检索：核对用户自己的历史信息；
- 时代背景检索：激活回忆、寻找自然话题。

## 3. 核心安全边界

时代背景只允许：

- 提示采访方向；
- 激活回忆；
- 形成自然问题；
- 帮助采访官理解年代背景。

时代背景不得自动：

- 写入 Story Summary；
- 写入 Story Agent Memory；
- 改变 Story Completion；
- 进入 Story Generation 作为用户个人事实；
- 推断用户一定经历过某个时代事件。

合法示例：

> “你刚才说 2001 年去了北京。那年北京申奥成功，你还记得当时城市里的气氛吗？”

非法推断：

> “你 2001 年在北京亲历了申奥成功。”

除非用户明确确认，否则外部时代事件永远不是用户事实。

## 4. 数据目标：时代记忆库，而不是新闻百科

每条内容应尽量短，建议 1～2 句概括。

优先覆盖：

- 时事 / 社会；
- 娱乐 / 影视 / 音乐；
- 体育；
- 科技 / 互联网；
- 消费 / 品牌 / 产品；
- 教育 / 校园；
- 工作 / 就业；
- 居住 / 交通 / 城市生活；
- 地方性事件；
- 具有一代人共同记忆的生活方式。

核心目标不是“知识完整”，而是：

> **这条时代信息能否帮助受访者想起自己的经历。**

## 5. 建议数据结构

```json
{
  "event_id": "cn-2001-beijing-olympic-bid",
  "start_year": 2001,
  "end_year": 2001,
  "country": "CN",
  "region": "北京",
  "categories": ["社会", "城市", "体育"],
  "title": "北京申奥成功",
  "summary": "2001 年 7 月，北京获得 2008 年夏季奥运会主办权。该事件在全国尤其北京引发广泛社会关注。",
  "keywords": ["北京", "申奥", "奥运会", "2001"],
  "life_stage_tags": ["求学", "初入职场", "工作", "城市生活"],
  "memory_trigger": "如果受访者当时在北京，可自然询问是否记得申奥成功当天或随后城市里的氛围。",
  "source_refs": []
}
```

正式实现前需要再冻结来源许可、数据更新方式与事实校验流程。

## 6. 检索条件

未来不建议只按“年份”搜索。

优先组合：

```text
年份 / 时间范围
+
受访者当时年龄
+
所在地
+
人生阶段
+
当前 Story 主题
```

例如：

```text
用户出生：1979
当前叙述：2001 年大学毕业去了北京

推导：
年龄约 22
地点：北京
人生阶段：毕业 / 初入职场
Story：第一次工作

时代背景检索：
1999～2003
+ 北京
+ 青年
+ 求职 / 城市生活 / 娱乐 / 社会热点
```

## 7. 时间窗口

人的年份记忆存在误差，因此默认不要只搜索单一年份。

未来建议按场景设置邻域，例如：

```text
明确年份：
year ± 1

“大概那几年”：
year ± 2

模糊阶段：
根据 Life Stage 起止时间确定
```

实际窗口必须通过访谈效果 Benchmark 后确定，不在当前 Future 文档中写死。

## 8. 从检索结果到采访提示

Retriever 不直接把大量事件原文塞给 Realtime Voice Model。

未来建议链路：

```text
Transcript Event
↓
时间 / 地点 / 年龄 / 人生阶段 / Story 主题信号
↓
时代背景检索
↓
相关性重排
↓
Slow Agent 选择 0～2 个候选
↓
生成短采访提示
↓
安全轮次边界
↓
Fast Realtime System
```

建议输出：

```json
{
  "based_on_turn_id": "turn_18",
  "era_hints": [
    {
      "background": "2001 年北京申奥成功，当时在北京社会关注度很高。",
      "reason": "用户刚提到 2001 年到北京工作",
      "suggestion": "如果自然，可询问他是否记得当时北京的城市氛围",
      "source_event_id": "cn-2001-beijing-olympic-bid"
    }
  ]
}
```

Realtime 采访官拥有最终选择权，可以：

- 使用；
- 改写；
- 忽略。

禁止为了“使用检索结果”而强行转移话题。

## 9. 触发原则

适合触发：

- 用户明确提到年份或时期；
- 用户进入新的 Life Stage；
- 用户明确提到过去所在城市 / 地区；
- 当前话题缺少自然追问方向；
- 用户出现“那时候有什么我也记不清了”等明显回忆困难；
- Slow Agent 判断时代线索可能帮助激活记忆。

不适合触发：

- 每个 Turn 固定检索；
- 用户正在讲高信息密度的个人故事时强行插入公共事件；
- 当前个人历史 Recall 已经提供更好的追问线索；
- 时代事件与当前 Story 只有弱相关；
- 为了展示 NVIDIA Retriever 而固定调用。

## 10. 与 NeMo Retriever 的关系

Future 可以维护两个逻辑上隔离的检索来源：

```text
个人历史证据索引
- Transcript 派生
- owner scoped
- 可从 SQLite 重建

时代背景索引
- 公共年代资料
- read-only
- 与用户私有数据隔离
```

两者都可以由 Classic Retrieval 提供低延迟召回。

个人历史复杂跨 Story / Session 搜索未来可升级 Agentic Retrieval。

时代背景检索默认不需要 Agentic Retrieval：

> **它的目标是快速找到少量高相关记忆触发器，而不是完成深度历史研究。**

## 11. 数据准备策略

未来实现时优先采用离线准备，而不是实时联网搜索：

```text
可信公共资料
↓
离线整理 / 去重 / 事实校验
↓
每事件 1～2 句摘要
↓
分类 + 年份 + 地域 + 人生阶段标签
↓
Embedding / Index
↓
DGX Spark 本地检索
```

好处：

- 延迟可控；
- Demo 稳定；
- 不依赖实时网络；
- 数据范围可审计；
- 可以提前做质量测试；
- 更适合 DGX Spark 本地部署叙事。

## 12. 第一阶段数据范围建议

如果未来进入比赛实现阶段，不建议一开始建设完整 70 年百科。

优先做能够覆盖演示故事的最小库：

- 中国大陆；
- 1970～2020；
- 每年精选几十个高记忆价值事件；
- 重点覆盖时事、社会、娱乐、音乐、影视、体育、科技、消费与城市生活；
- Demo 用户涉及的年份和地区优先加密度。

数据规模不需要很大。

真正衡量标准应是：

> **时代背景是否提高了有效追问率和回忆唤起率。**

## 13. Future Benchmark

正式接入前至少评测：

- 检索相关率；
- 无关时代话题注入率；
- 用户事实污染率必须为 0；
- 实时检索 P50 / P95；
- 每轮不必要检索率；
- 时代提示被 Realtime Agent 实际采用的比例；
- 使用时代提示后是否产生新的有效用户事实。

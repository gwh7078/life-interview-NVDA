# 时代背景检索库设计 v1.2

> Status: **Future / Planned / Deferred**
>
> Date: 2026-09-20
>
> 当前版本不开发、不计入已实现能力。本文件只冻结未来产品与技术方向。
>
> 第一版进一步收敛：**暂不做地域维度，不预存建议提问，不预存适合人群、人生阶段标签或记忆价值评分。**

## 1. 目标

未来 Realtime Slow System 除了回忆“用户以前说过什么”，还可以检索：

> **用户当时所处年代发生过什么、流行什么、社会在讨论什么。**

目的不是补充用户事实，而是帮助采访官获得新的话题线索、唤起用户回忆。

时代背景永远只是外部背景。只有用户自己在采访中确认的信息，才可能进入用户事实链路。

## 2. 第一版最小数据结构

时代背景库第一版只保留 5 个字段：

```json
{
  "start_year": 2000,
  "end_year": 2001,
  "category": "娱乐",
  "title": "周杰伦开始走红",
  "summary": "2000年前后，周杰伦发行首张专辑并迅速受到年轻人关注。其音乐风格逐渐成为当时华语流行文化的重要组成部分。"
}
```

字段说明：

- `start_year`：事件或时代现象开始年份；
- `end_year`：结束年份；单年事件可与 start_year 相同；
- `category`：时事、社会、娱乐、音乐、影视、体育、科技、互联网、消费、教育、工作、生活等；
- `title`：简短标题；
- `summary`：1～2 句事实背景。

第一版明确不保存：

- 地域；
- 建议提问；
- 适合人群；
- 人生阶段标签；
- 记忆价值评分；
- keywords；
- 模型生成的采访话术。

原则：

> **时代库只负责提供可检索的背景事实；怎么使用这些事实，由慢系统结合当前对话决定。**

## 3. 为什么用开始年份 + 结束年份

时代记忆不一定发生在某一个精确年份。

例如：

```json
{
  "start_year": 1999,
  "end_year": 2002,
  "category": "互联网",
  "title": "网吧与QQ逐渐普及",
  "summary": "2000年前后，网吧和即时聊天逐渐进入年轻人的日常生活。很多人第一次接触互联网、网友和网络游戏都发生在这一时期。"
}
```

因此统一使用 `start_year` 与 `end_year`，比只保存一个 year 更适合时代现象。

## 4. Future 检索流程

第一版采用非常简单的两级检索：

```text
当前对话
↓
慢系统识别用户正在谈论的大概年份 / 时间范围
↓
第一层：年份范围过滤
↓
第二层：标题 + 摘要语义检索
↓
返回少量候选背景
↓
慢系统结合完整对话判断是否值得使用
↓
生成 0～1 条话题提示
↓
Realtime 决定如何自然表达
```

例如用户说：

> “我大概 2000 年左右刚参加工作。”

慢系统未来可以把检索范围设置为：

```text
1998 ～ 2002
```

先过滤出与这个时间窗口重叠的记录，再对 `title + summary` 做语义检索。

## 5. 年份过滤规则

事件与查询时间窗口有重叠即可进入候选集合：

```text
event.start_year <= query_end_year
AND
event.end_year >= query_start_year
```

例如：

```text
查询：1998～2002

记录 A：2001～2001
→ 命中

记录 B：1999～2002
→ 命中

记录 C：2005～2006
→ 排除
```

这样可以在向量检索之前先排除大量无关年代。

## 6. 为什么第一版暂时不要地域

地域能够提高精度，但也会明显增加：

- 数据准备复杂度；
- 地域层级设计；
- 全国事件与地方事件兼容问题；
- 城市改名 / 行政区划问题；
- 检索逻辑与数据量。

第一版目标只是验证：

> **时代背景检索能否真实提高采访中的回忆唤起和有效追问。**

因此暂时只使用时间范围 + 语义相关性。未来真实测试证明“全国背景太泛”时，再增加地域字段。

## 7. 不预存建议问题

时代库不保存类似：

> “你当年喜欢周杰伦吗？”

因为同一条背景在不同对话里的使用方式完全不同。

例如检索结果是“周杰伦开始走红”：

- 当前上下文是大学宿舍生活时，慢系统可能建议聊当时宿舍里听什么歌；
- 当前上下文是第一次工作时，慢系统可能直接丢弃这个结果。

因此职责冻结为：

```text
时代背景库
= 提供背景事实

Skill Script
= `era-context-search.mjs` 调用 Retriever 找到相关背景

Slow Agent
= 判断值不值得聊、与当前故事怎么连接

Realtime
= 最终如何自然表达
```

## 8. 数据内容方向

时代背景库不是“重大新闻库”，而是“时代记忆库”。

优先收录：

- 时事 / 社会；
- 娱乐 / 影视 / 音乐；
- 体育；
- 科技 / 互联网；
- 消费产品；
- 校园文化；
- 工作 / 就业；
- 日常生活方式。

很多普通生活背景比重大新闻更适合唤起个人回忆，例如：

- 第一次申请 QQ；
- 第一次去网吧；
- BP 机到手机；
- VCD / DVD / 租碟；
- 磁带、CD、MP3；
- 早期电脑游戏；
- 商品房与装修；
- 大型超市逐渐普及。

## 9. 与 NeMo Retriever 的关系

Future 时代背景库使用独立只读索引：

```text
Era Context Index
↓
年份元数据过滤
↓
Classic Retrieval
↓
Reranker（如有必要）
↓
少量候选背景
```

默认不使用 Agentic Retrieval。

原因：

> **时代背景检索需要的是快、少、相关，而不是深度历史研究。**

## 10. 与用户事实的硬边界

时代背景只允许：

- 提供采访线索；
- 帮助理解年代；
- 激活用户回忆；
- 形成自然话题。

不得自动：

- 写入 Story Summary；
- 写入 Story Agent Memory；
- 改变 Story Completion；
- 作为 Story Generation 中的用户个人事实；
- 推断用户一定经历过某个公共事件。

例如时代库命中“2001 年北京申奥成功”，只能帮助采访官寻找话题。

只有用户明确说：

> “我记得那天我们单位所有人都在看电视。”

这句话本身才属于新的用户采访证据。

## 11. Future 第一阶段数据范围

如果后续真正开发，第一阶段不做完整百科。

建议先做：

- 中国大陆；
- 1970～2020；
- 每年 / 每个时间段精选高记忆价值事件与生活现象；
- 每条 1～2 句；
- 优先覆盖社会、娱乐、音乐、影视、体育、互联网、消费和生活方式。

第一阶段衡量的不是数据量，而是：

> **能否找到真正有助于用户继续回忆的话题。**

## 12. Future Benchmark

正式接入前至少评测：

- 年份过滤正确率；
- 检索相关率；
- 无关时代话题注入率；
- 用户事实污染率必须为 0；
- 检索延迟 P50 / P95；
- 慢系统最终采用时代背景的比例；
- 使用时代背景后是否产生新的有效用户事实。

## 14. Future Skill Script 形态

时代背景检索不向模型注册专用 `era_context_search` Product Tool。

Future Realtime Slow Agent 使用：

```text
agent/skills/interview-observer/
└── scripts/
    └── era-context-search.mjs
```

Agent 只提供时间范围与查询意图；脚本内部完成年份过滤、Retriever 调用、rerank、Top-K 裁剪和统一 JSON 返回。

底层通过 OpenClaw 受限通用 exec 运行脚本，但模型不需要读取复杂 Tool Schema。

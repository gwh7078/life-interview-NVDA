## 一、原始素材日志

### 2026-09-21

#### 1. 先把“十日谈”当素材库，而不是现在就写文章

目前决定在开发期间持续记录零散想法。每当出现值得保留的产品判断、技术取舍、踩坑、架构变化或个人感受，就先写到这里。

等项目接近提交时，再基于这些记录整理出最终征文，而不是每天为了“写文章”打断开发。

#### 2. 一对在天津卖家具的夫妻，也来参加 DGX Spark 技术比赛

团队背景本身可能就是这篇十日谈最重要的一条叙事线：

我们不是软件工程师，也不是 AI 实验室团队，而是一对在天津做家具营销的夫妻。团队只有两个人，没有程序员伙伴，也没有熟悉技术圈的朋友，基本就是夫妻两个人硬着头皮做。

这件事之所以可能发生，一个很重要的背景，是过去一两年 AI 编程能力快速进步。以前，一个几乎没有完整软件开发能力的人，很难独立完成一个涉及前端、后端、数据库、Agent Runtime、Memory、RAG、实时语音和本地部署的产品；现在，借助 AI，可以边做、边问、边查、边推翻，再重新搭起来。

因此，这次参赛本身也可以被看作一个案例：**一对完全不懂传统软件开发、在天津卖家具的夫妻，也能够进入一个高度技术化的 Agent Skills / DGX Spark 黑客松。**

这并不意味着技术门槛消失了。恰恰相反，很多地方仍然非常难，只是 AI 把“必须先系统学习几年才能开始做”变成了“可以先做，在真实问题里不断学习”。

#### 3. 我为什么开始接触 Agent

真正开始接触 Agent，大约是从 OpenClaw 在 2025 年走红之后。

最初动机非常实际：卖家具也有很多重复、琐碎、需要整理信息和反复处理的工作，所以希望找一个“智能助理”把这些事情自动化。

当时试用了 OpenClaw，也开始理解 Agent 能做什么。但那一阶段产品和生态还不够成熟，实际工作中并没有立刻带来特别大的帮助。

不过这段经历留下了一个很重要的积累：虽然不会传统软件开发，但对 Agent Runtime、上下文、Memory 等概念，比前端、后端、数据库这些传统工程模块更早接触，也理解得更深一些。

这次做“人生采访局”时，真正比较熟悉的技术领域，反而就是 Agent、Runtime、Memory 这一块。

#### 4. 我们到底有多“菜”

这部分最好在最终文章中保留，因为它决定了整个开发过程为什么会这么曲折。

除了此前使用 Agent，对 Runtime、Memory 等有一些理解之外：

- 前端：只有非常模糊的概念；
- 后端 / 中台：只有模糊概念；
- 数据库：知道它存在，但缺乏系统设计能力；
- 软件架构：没有传统工程训练；
- DGX Spark：此前只是听说过，没有真正了解和接触过；
- NVIDIA 本地 AI 技术栈：基本从零开始。

所以“人生采访局”实际上远远超出了两个人原有的技术能力。

这个产品表面上看只是“AI 帮人做回忆录”，但真正做下去以后，会遇到大量复杂问题：

- 一个故事的数据到底怎么存；
- Transcript、Summary、Story State、Memory 分别是什么；
- 多轮访谈怎样保持一致；
- 如何避免模型把猜测写成事实；
- 采访结束后如何可靠地更新状态；
- 实时语音怎样既保持低延迟，又能利用历史上下文；
- Agent、Skill、脚本、Tool 到底应该怎么分层；
- 哪些任务应该实时完成，哪些任务应该异步或放到慢系统；
- 本地模型、云端实时语音与 DGX Spark 怎么划边界。

这些问题远远不是“让大模型写几个页面”能解决的。

#### 5. “人生采访局”实际上逼着我们补了一整套技术课

这个项目对数据架构、业务逻辑和系统架构的要求，明显超过了团队原本的能力。

很多概念不是提前学完再开发，而是在遇到真实问题以后才被迫搞懂：

先做一个版本 → 发现逻辑有问题 → 查资料 → 问 AI → 重构 → 测试 → 又发现新的问题 → 再推翻。

很多版本其实都是这样被推倒重来的。

在这个过程中，才逐步理解：

- 为什么实时语音不能把所有复杂推理都塞在一条链路里；
- 为什么需要“快系统 / 慢系统”；
- 为什么普通 Retrieval 和 Agentic Retrieval 应该承担不同任务；
- 为什么 Memory 不能简单等于 Transcript；
- 为什么有些能力应该是 Agent Skill，而 Skill 里面又应该尽量调用确定性脚本；
- 为什么产品的数据结构会反过来决定 Agent 是否可靠。

这些架构不是一开始设计出来的，而是在反复失败之后逐步长出来的。

#### 6. 夫妻店开发，还带着两个幼儿园阶段的孩子

这次开发还有一个很现实的背景：团队不仅只有夫妻两个人，还要同时照顾两个年幼的孩子。

比赛开发期间，两个人又生病，新冠再次阳性。

本来因为技术能力不足，开发速度就不快，而且经常出现“做了几天 → 发现方向不对 → 推倒重来”的情况；生病、照顾孩子和比赛时间限制叠加以后，进度进一步受到影响。

这部分最终成文时不需要刻意煽情，但可以真实写出来。它解释了为什么很多开发不是理想状态下的工程实践，而是在非常有限的时间、精力和技术能力下做取舍。

#### 7. DGX Spark 是这次额外增加的一座山

即使只把 Web 版本的“人生采访局”做好，对我们来说已经很难。

但这次比赛又增加了一个此前几乎完全陌生的变量：DGX Spark。

参加比赛前，对 DGX Spark 只是“听说过”的程度，并没有真正接触过：

- 不熟悉机器本身；
- 不熟悉本地模型部署；
- 不熟悉 NVIDIA 的 Agent / RAG / NIM / NeMo 等生态；
- 不确定 ARM 架构、本地推理和现有 Web 服务之间应该怎样组合；
- 开发阶段手里甚至没有 DGX Spark 实机。

所以这次挑战实际上有两层：

第一层是把“人生采访局”从一个 Web AI 产品继续重构成真正的 Agent Native 系统；

第二层是再把它迁移到 DGX Spark 和 NVIDIA 技术栈上。

这也是十日谈后续值得重点记录的主线之一：**一个此前没碰过 DGX Spark 的非技术团队，是怎样一步步把它拆解、理解并接入产品的。**


#### 8. “人生采访局”为什么会出现

这个产品最早不是为了比赛，也不是为了做一个“AI Demo”。

起点来自家里的一件事。

岳父曾经出过一本书。后来想到父亲当时有一些轻度抑郁情绪，我觉得如果能让他把自己这些年的经历写下来，也许既能留下东西，也能在整理回忆的过程中帮助他舒缓情绪、改善精神状态。

于是最初的想法很简单：也让父亲写一本属于自己的书。

但现实问题很快出现了——他没有兴趣自己坐下来写，而且也不知道怎么写。

所以我开始反过来想：如果不是让他“写”，而是让一个 AI 像记者一样和他聊天、采访，再把这些内容整理成回忆录，会不会更现实？

最早的一版设想，就是把 OpenClaw 接到他的微信上，通过几个 Skills 持续和他聊天、提问、整理内容，最后帮助完成一本回忆录，甚至进一步准备出版。

这个方向当时其实已经尝试过，但没有真正做成。

主要限制不是想法，而是当时的技术条件：

- OpenClaw 当时的 Agent Harness 还比较不成熟；
- 大模型长上下文能力明显不够；
- 长期访谈过程中容易发生遗漏；
- 多轮整理后容易产生事实幻觉；
- 前面已经聊过的重要信息，后面不一定还能稳定召回；
- 有些任务甚至需要在 OpenClaw、豆包、ima 等不同工具之间来回配合。

也就是说，当时“让 AI 陪一个人连续聊很久，再可靠地整理成一本书”这件事，表面上看只是聊天，实际上对上下文管理、Memory、事实一致性、访谈状态和后处理链路的要求非常高。

所以这个想法没有消失，只是暂时搁置了。

到了 2026 年，情况开始发生变化：

- 大模型长上下文能力明显提升；
- Agent Harness 比之前成熟；
- Memory、Retrieval、结构化数据和多 Agent 协作的方案更完整；
- 实时语音能力开始可以真正承担长访谈；
- 本地模型和边缘算力也让隐私与长期资料处理有了新的可能。

因此，“人生采访局”这次并不是突然想出来的新项目。

更准确地说，它是一个**去年因为技术条件不成熟而没有做成的家庭项目，在模型、Agent 和本地 AI 技术成熟以后，被重新捡起来了。**

这也是为什么我们对这个项目有比较强的执念：它最早不是为了参赛，而是从“能不能帮父亲把一生讲出来”这个非常具体的问题开始的。


#### 9. 为什么回忆录值得被留下来

我后来越来越觉得，做回忆录这件事本身非常有价值，而且它的价值不只是“出一本书”。

第一层，是对一个人自己有价值。

把一生经历重新讲一遍、梳理一遍，本身就是一次回望。很多过去没有整理过的经历、情绪和关系，会在讲述过程中重新被看见。对于一些中老年人来说，这种回顾可能也有助于舒缓情绪，让他们重新确认自己这一生经历过什么、做过什么、爱过什么、失去过什么。

第二层，是对家人有价值。

父亲的回忆录，对孩子来说并不是一本“已经知道的故事”。

恰恰相反，它很可能是一本全新的故事。

作为孩子，我们真正认识父亲，是从自己出生以后开始的；而即使在出生以后，他生活中的大量经历，我们也没有在场。他年轻时经历过什么、做过什么选择、害怕过什么、为什么做出某些决定、当时怎么想，我们往往并不知道。

家庭成员之间长期相处，并不等于真正了解彼此。

一本回忆录，可以让孩子第一次从父亲自己的视角，重新认识这个人。它留下的不只是“发生过什么”，还有这个人的所思所想。

再往后看，它也是留给后人的一份人格档案。

照片可以留下样子，族谱可以留下名字，但一个人的声音、记忆、判断、情绪和人生经验，如果没有被记录，往往会随着时间快速消失。

所以“人生采访局”真正想保存的，不只是一本书，而是一个人曾经怎样活过、怎样理解自己的人生。

#### 10. 文章开头必须保留的核心句

最终“十日谈”成文时，文章开头优先围绕下面这个意思展开：

> **一个人的肉体死亡，并不一定是最后的死亡。真正的消失，是这个世界上再也没有人记得他。**

这句话目前先作为**主题意译**保存，正式发布前再核对是否存在准确原句及可靠出处，避免错误署名。

这句话后面可以直接接“人生采访局”的产品动机：

> 如果记忆是一个人留在世界上的最后一部分，那么回忆录做的事情，就是尽量让这部分东西多留一会儿。

然后再进入父亲的故事：

> 我对父亲的了解，其实是从我出生以后才开始的。即便如此，他人生中大量的经历我从未在场，他真正的所思所想，我也未必知道。也许一本回忆录，反而能让我第一次完整地认识自己的父亲。

这可以作为整篇文章的情感起点，再往后转入“为什么后来想用 Agent 来完成这件事”。


#### 11. 两个人怎么分工：产品理解、测试执行和 AI 共创

因为我们两个人都没有传统软件开发背景，所以这次开发不可能按照正常技术团队那样分成前端、后端、测试、架构几个岗位。

我们的分工更多是按照“谁更理解问题”来形成的。

我之前已经做过一版回忆录产品，所以对这个领域的用户需求、用户行为、采访过程以及周边问题更熟悉。哪些地方用户容易卡住、什么问题适合追问、什么信息应该保存、回忆录最终怎么组织，这些判断主要由我来负责。

所以产品设计、核心流程以及很多关键业务判断，基本以我为主。

我太太此前对回忆录这个领域几乎不了解，但她反而更适合承担另一部分工作：大量的真实测试、测试用例设计、资料收集、信息核对，以及让 Agent 帮忙执行这些重复但非常重要的工作。

尤其这是一个语音交互产品，很多问题只有真正开口说、连续聊、反复测才能暴露出来。比如：

- 什么时候 Agent 会突然不回应；
- 第一个问题听起来是否自然；
- 追问会不会太机械；
- 用户说了一大段以后，系统还能不能抓住重点；
- 续访和首次采访的体验是否一致；
- 第三方补充故事时，身份关系有没有说清楚；
- 采访结束以后，页面和总结链路有没有真正闭环。

这些问题单看代码很难发现，所以大量测试和测试设计由她来推动，再让 Agent 帮忙整理日志、生成测试用例、对比不同版本。

至于系统架构、数据结构、Agent Runtime、Memory、Retrieval、Skill 这些我们自己原本并不具备完整能力的部分，基本是我不断和 AI 讨论出来的。

通常的过程不是“AI 给一个方案我们照着做”，而是：

> 我先描述真实业务问题 → AI 提方案 → 我结合产品理解质疑 → 再查资料 → 再讨论 → 做出来 → 实测 → 发现问题 → 推翻一部分 → 重新设计。

因此，如果一定要给这个团队画一张组织结构图，可能更接近：

- **我：产品负责人 + 业务架构决策；**
- **太太：测试负责人 + 用户体验验证 + 信息收集；**
- **AI：技术顾问 + 架构讨论对象 + 开发执行 + 测试辅助。**

这也是这次开发很有意思的一点：

**AI 不只是帮我们“写代码”，而是第一次让两个缺少完整软件工程能力的人，可以临时拼出一个过去需要多个专业岗位才能运转的小型产品团队。**

## 四、潜在主叙事

目前最有力量的一条主线不是“我们用了多少 NVIDIA 技术”，而是：

> **过去，完成这样一个产品可能需要一个具备产品、前端、后端、数据库和 AI 工程能力的小团队；现在，一对在天津卖家具、没有传统软件开发背景的夫妻，也能够借助 AI，在真实问题中学习这些知识，并最终走进 DGX Spark Agent Skills 黑客松。**

这里不能写成“AI 已经让技术不重要”。

更准确的表达应该是：

> **AI 没有消灭技术门槛，但它显著降低了进入技术世界的前置门槛。过去要先学会很多东西，才有资格开始；现在可以先开始，然后被真实的问题逼着学习。**

“人生采访局”的整个开发过程，恰好可以作为这个变化的一个真实样本。

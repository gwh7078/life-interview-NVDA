## 一、原始素材日志

### 2026-09-21

#### 1. 先把“十日谈”当素材库，而不是现在就写文章

目前决定在开发期间持续记录零散想法。每当出现值得保留的产品判断、技术取舍、踩坑、架构变化或个人感受，就先写到这里。

等项目接近提交时，再基于这些记录整理出最终征文，而不是每天为了“写文章”打断开发。

#### 2. 一对在天津卖家具的夫妻，也来参加 DGX Spark 技术比赛

团队背景本身可能就是这篇十日谈最重要的一条叙事线：

我们不是软件工程师，也不是 AI 实验室团队，而是一对在天津做家具营销的夫妻。团队只有两个人，没有程序员伙伴，也没有熟悉技术圈的朋友，基本就是夫妻两个人硬着头皮做。

这件事之所以可能发生，一个很重要的背景，是过去一两年 AI 编程能力快速进步。以前，一个几乎没有完整软件开发能力的人，很难独立完成一个涉及前端、后端、数据库、Agent Runtime、Memory、RAG、实时语音和本地部署的产品；现在，借助 AI，可以边做、边问、边查、边推翻，再重新搭起来。

因此，这次参赛本身也可以被看作一个案例：**一对完全不懂传统软件开发、在天津卖家具的夫妻，也能够进入一个高度技术化的 Agent Skills / DGX Spark 黑客松。**

这并不意味着技术门槛消失了。恰恰相反，很多地方仍然非常难，只是 AI 把“必须先系统学习几年才能开始做”变成了“可以先做，在真实问题里不断学习”。

#### 3. 我为什么开始接触 Agent

真正开始接触 Agent，大约是从 OpenClaw 在 2025 年走红之后。

最初动机非常实际：卖家具也有很多重复、琐碎、需要整理信息和反复处理的工作，所以希望找一个“智能助理”把这些事情自动化。

当时试用了 OpenClaw，也开始理解 Agent 能做什么。但那一阶段产品和生态还不够成熟，实际工作中并没有立刻带来特别大的帮助。

不过这段经历留下了一个很重要的积累：虽然不会传统软件开发，但对 Agent Runtime、上下文、Memory 等概念，比前端、后端、数据库这些传统工程模块更早接触，也理解得更深一些。

这次做“人生采访局”时，真正比较熟悉的技术领域，反而就是 Agent、Runtime、Memory 这一块。

#### 4. 我们到底有多“菜”

这部分最好在最终文章中保留，因为它决定了整个开发过程为什么会这么曲折。

除了此前使用 Agent，对 Runtime、Memory 等有一些理解之外：

- 前端：只有非常模糊的概念；
- 后端 / 中台：只有模糊概念；
- 数据库：知道它存在，但缺乏系统设计能力；
- 软件架构：没有传统工程训练；
- DGX Spark：此前只是听说过，没有真正了解和接触过；
- NVIDIA 本地 AI 技术栈：基本从零开始。

所以“人生采访局”实际上远远超出了两个人原有的技术能力。

这个产品表面上看只是“AI 帮人做回忆录”，但真正做下去以后，会遇到大量复杂问题：

- 一个故事的数据到底怎么存；
- Transcript、Summary、Story State、Memory 分别是什么；
- 多轮访谈怎样保持一致；
- 如何避免模型把猜测写成事实；
- 采访结束后如何可靠地更新状态；
- 实时语音怎样既保持低延迟，又能利用历史上下文；
- Agent、Skill、脚本、Tool 到底应该怎么分层；
- 哪些任务应该实时完成，哪些任务应该异步或放到慢系统；
- 本地模型、云端实时语音与 DGX Spark 怎么划边界。

这些问题远远不是“让大模型写几个页面”能解决的。

#### 5. “人生采访局”实际上逼着我们补了一整套技术课

这个项目对数据架构、业务逻辑和系统架构的要求，明显超过了团队原本的能力。

很多概念不是提前学完再开发，而是在遇到真实问题以后才被迫搞懂：

先做一个版本 → 发现逻辑有问题 → 查资料 → 问 AI → 重构 → 测试 → 又发现新的问题 → 再推翻。

很多版本其实都是这样被推倒重来的。

在这个过程中，才逐步理解：

- 为什么实时语音不能把所有复杂推理都塞在一条链路里；
- 为什么需要“快系统 / 慢系统”；
- 为什么普通 Retrieval 和 Agentic Retrieval 应该承担不同任务；
- 为什么 Memory 不能简单等于 Transcript；
- 为什么有些能力应该是 Agent Skill，而 Skill 里面又应该尽量调用确定性脚本；
- 为什么产品的数据结构会反过来决定 Agent 是否可靠。

这些架构不是一开始设计出来的，而是在反复失败之后逐步长出来的。

#### 6. 夫妻店开发，还带着两个幼儿园阶段的孩子

这次开发还有一个很现实的背景：团队不仅只有夫妻两个人，还要同时照顾两个年幼的孩子。

比赛开发期间，两个人又生病，新冠再次阳性。

本来因为技术能力不足，开发速度就不快，而且经常出现“做了几天 → 发现方向不对 → 推倒重来”的情况；生病、照顾孩子和比赛时间限制叠加以后，进度进一步受到影响。

这部分最终成文时不需要刻意煽情，但可以真实写出来。它解释了为什么很多开发不是理想状态下的工程实践，而是在非常有限的时间、精力和技术能力下做取舍。

#### 7. DGX Spark 是这次额外增加的一座山

即使只把 Web 版本的“人生采访局”做好，对我们来说已经很难。

但这次比赛又增加了一个此前几乎完全陌生的变量：DGX Spark。

参加比赛前，对 DGX Spark 只是“听说过”的程度，并没有真正接触过：

- 不熟悉机器本身；
- 不熟悉本地模型部署；
- 不熟悉 NVIDIA 的 Agent / RAG / NIM / NeMo 等生态；
- 不确定 ARM 架构、本地推理和现有 Web 服务之间应该怎样组合；
- 开发阶段手里甚至没有 DGX Spark 实机。

所以这次挑战实际上有两层：

第一层是把“人生采访局”从一个 Web AI 产品继续重构成真正的 Agent Native 系统；

第二层是再把它迁移到 DGX Spark 和 NVIDIA 技术栈上。

这也是十日谈后续值得重点记录的主线之一：**一个此前没碰过 DGX Spark 的非技术团队，是怎样一步步把它拆解、理解并接入产品的。**


#### 8. “人生采访局”为什么会出现

这个产品最早不是为了比赛，也不是为了做一个“AI Demo”。

起点来自家里的一件事。

岳父曾经出过一本书。后来想到父亲当时有一些轻度抑郁情绪，我觉得如果能让他把自己这些年的经历写下来，也许既能留下东西，也能在整理回忆的过程中帮助他舒缓情绪、改善精神状态。

于是最初的想法很简单：也让父亲写一本属于自己的书。

但现实问题很快出现了——他没有兴趣自己坐下来写，而且也不知道怎么写。

所以我开始反过来想：如果不是让他“写”，而是让一个 AI 像记者一样和他聊天、采访，再把这些内容整理成回忆录，会不会更现实？

最早的一版设想，就是把 OpenClaw 接到他的微信上，通过几个 Skills 持续和他聊天、提问、整理内容，最后帮助完成一本回忆录，甚至进一步准备出版。

这个方向当时其实已经尝试过，但没有真正做成。

主要限制不是想法，而是当时的技术条件：

- OpenClaw 当时的 Agent Harness 还比较不成熟；
- 大模型长上下文能力明显不够；
- 长期访谈过程中容易发生遗漏；
- 多轮整理后容易产生事实幻觉；
- 前面已经聊过的重要信息，后面不一定还能稳定召回；
- 有些任务甚至需要在 OpenClaw、豆包、ima 等不同工具之间来回配合。

也就是说，当时“让 AI 陪一个人连续聊很久，再可靠地整理成一本书”这件事，表面上看只是聊天，实际上对上下文管理、Memory、事实一致性、访谈状态和后处理链路的要求非常高。

所以这个想法没有消失，只是暂时搁置了。

到了 2026 年，情况开始发生变化：

- 大模型长上下文能力明显提升；
- Agent Harness 比之前成熟；
- Memory、Retrieval、结构化数据和多 Agent 协作的方案更完整；
- 实时语音能力开始可以真正承担长访谈；
- 本地模型和边缘算力也让隐私与长期资料处理有了新的可能。

因此，“人生采访局”这次并不是突然想出来的新项目。

更准确地说，它是一个**去年因为技术条件不成熟而没有做成的家庭项目，在模型、Agent 和本地 AI 技术成熟以后，被重新捡起来了。**

这也是为什么我们对这个项目有比较强的执念：它最早不是为了参赛，而是从“能不能帮父亲把一生讲出来”这个非常具体的问题开始的。


#### 9. 为什么回忆录值得被留下来

我后来越来越觉得，做回忆录这件事本身非常有价值，而且它的价值不只是“出一本书”。

第一层，是对一个人自己有价值。

把一生经历重新讲一遍、梳理一遍，本身就是一次回望。很多过去没有整理过的经历、情绪和关系，会在讲述过程中重新被看见。对于一些中老年人来说，这种回顾可能也有助于舒缓情绪，让他们重新确认自己这一生经历过什么、做过什么、爱过什么、失去过什么。

第二层，是对家人有价值。

父亲的回忆录，对孩子来说并不是一本“已经知道的故事”。

恰恰相反，它很可能是一本全新的故事。

作为孩子，我们真正认识父亲，是从自己出生以后开始的；而即使在出生以后，他生活中的大量经历，我们也没有在场。他年轻时经历过什么、做过什么选择、害怕过什么、为什么做出某些决定、当时怎么想，我们往往并不知道。

家庭成员之间长期相处，并不等于真正了解彼此。

一本回忆录，可以让孩子第一次从父亲自己的视角，重新认识这个人。它留下的不只是“发生过什么”，还有这个人的所思所想。

再往后看，它也是留给后人的一份人格档案。

照片可以留下样子，族谱可以留下名字，但一个人的声音、记忆、判断、情绪和人生经验，如果没有被记录，往往会随着时间快速消失。

所以“人生采访局”真正想保存的，不只是一本书，而是一个人曾经怎样活过、怎样理解自己的人生。

#### 10. 文章开头必须保留的核心句

最终“十日谈”成文时，文章开头优先围绕下面这个意思展开：

> **一个人的肉体死亡，并不一定是最后的死亡。真正的消失，是这个世界上再也没有人记得他。**

这句话目前先作为**主题意译**保存，正式发布前再核对是否存在准确原句及可靠出处，避免错误署名。

这句话后面可以直接接“人生采访局”的产品动机：

> 如果记忆是一个人留在世界上的最后一部分，那么回忆录做的事情，就是尽量让这部分东西多留一会儿。

然后再进入父亲的故事：

> 我对父亲的了解，其实是从我出生以后才开始的。即便如此，他人生中大量的经历我从未在场，他真正的所思所想，我也未必知道。也许一本回忆录，反而能让我第一次完整地认识自己的父亲。

这可以作为整篇文章的情感起点，再往后转入“为什么后来想用 Agent 来完成这件事”。


#### 11. 两个人怎么分工：产品理解、测试执行和 AI 共创

因为我们两个人都没有传统软件开发背景，所以这次开发不可能按照正常技术团队那样分成前端、后端、测试、架构几个岗位。

我们的分工更多是按照“谁更理解问题”来形成的。

我之前已经做过一版回忆录产品，所以对这个领域的用户需求、用户行为、采访过程以及周边问题更熟悉。哪些地方用户容易卡住、什么问题适合追问、什么信息应该保存、回忆录最终怎么组织，这些判断主要由我来负责。

所以产品设计、核心流程以及很多关键业务判断，基本以我为主。

我太太此前对回忆录这个领域几乎不了解，但她反而更适合承担另一部分工作：大量的真实测试、测试用例设计、资料收集、信息核对，以及让 Agent 帮忙执行这些重复但非常重要的工作。

尤其这是一个语音交互产品，很多问题只有真正开口说、连续聊、反复测才能暴露出来。比如：

- 什么时候 Agent 会突然不回应；
- 第一个问题听起来是否自然；
- 追问会不会太机械；
- 用户说了一大段以后，系统还能不能抓住重点；
- 续访和首次采访的体验是否一致；
- 第三方补充故事时，身份关系有没有说清楚；
- 采访结束以后，页面和总结链路有没有真正闭环。

这些问题单看代码很难发现，所以大量测试和测试设计由她来推动，再让 Agent 帮忙整理日志、生成测试用例、对比不同版本。

至于系统架构、数据结构、Agent Runtime、Memory、Retrieval、Skill 这些我们自己原本并不具备完整能力的部分，基本是我不断和 AI 讨论出来的。

通常的过程不是“AI 给一个方案我们照着做”，而是：

> 我先描述真实业务问题 → AI 提方案 → 我结合产品理解质疑 → 再查资料 → 再讨论 → 做出来 → 实测 → 发现问题 → 推翻一部分 → 重新设计。

因此，如果一定要给这个团队画一张组织结构图，可能更接近：

- **我：产品负责人 + 业务架构决策；**
- **太太：测试负责人 + 用户体验验证 + 信息收集；**
- **AI：技术顾问 + 架构讨论对象 + 开发执行 + 测试辅助。**

这也是这次开发很有意思的一点：

**AI 不只是帮我们“写代码”，而是第一次让两个缺少完整软件工程能力的人，可以临时拼出一个过去需要多个专业岗位才能运转的小型产品团队。**


#### 12. 这十天一直有一个问题：我们到底能不能做完

报名以后，其实并没有一种“既然参加了，那就一定能做完”的确定感。

恰恰相反，这十天里反复出现的一个念头就是：

> **能不能完成？能不能完成？到底能不能完成？**

这种忐忑几乎每天都在。

很奇怪的是，每天其实都能看到明显进展。

今天把一个模块跑通了，感觉往前走了一大截；明天把一个架构问题想明白了，又觉得终于接近目标；某个测试通过的时候，也会短暂觉得“好像真的快做出来了”。

但只要再往后看一点，就会发现前面又冒出来一大片新的问题：

- 这个模块能跑了，但和其他模块还没真正接起来；
- Web 版本稳定了，但 Agent 化还没做完；
- Agent 能工作了，但 Memory 还有问题；
- Memory 理顺了，实时语音又暴露新的延迟和上下文问题；
- 产品逻辑刚刚稳定，又要考虑 DGX Spark、本地部署和 NVIDIA 技术栈；
- 代码能跑以后，还要准备测试、文档、Demo、视频和最终提交。

所以整个十天并不是一条“每天完成 10%，最后刚好 100%”的直线。

更像是：

> **每天都往前走了一大截，但每天也都会看见更远的地方。**

甚至有时候，理解得越多，反而越清楚自己还有多少东西没做。

这可能也是两个非技术背景的人参加这种比赛最真实的感受：不是一直相信自己一定能完成，而是在“好像快做出来了”和“这怎么可能做得完”之间来回摆动。

真正推动项目继续往前的，也不是某个完整规划，而是每天只先把眼前最重要的那一块解决掉，再去看下一块。

最终文章里，这段可以作为贯穿十天的一条情绪线，而不是只在结尾写一句“过程很艰难”。


### 2026-09-24

#### 13. 为什么最后一定要做“实时语音采访”

最早给父亲配置 OpenClaw 时，微信语音还不能直接传进 OpenClaw。

父亲其实并不愿意打字，所以他经常问我一件事：

> 能不能像豆包一样，直接发语音？

这件事后来变成了产品设计里一个很关键的线索。

一开始，我也觉得“能发语音消息”可能已经够了。但后来观察实际使用后发现，语音消息一来一回，即使两个人聊了半小时，真正采集到的信息量其实并不高。

它和“连续通话半小时”完全不是一个量级。

回忆录这种场景里，很多细节不是靠一次性提问得到的，而是在对方刚说完一件事以后，马上顺着里面的细节继续追问。只要中间不断被“录一段—发送—等待—再录一段”切断，信息密度和情绪连续性都会明显下降。

所以后来逐渐形成一个判断：

> **对回忆录来说，实时语音采访不是一个体验升级，而是信息采集效率最高的核心交互方式。**

也正因为这个判断，后面才会真正去啃实时语音、VAD、判停、打断、上下文注入、快慢系统这些原本完全不懂的技术问题。

#### 14. 第一次看到父亲讲出我从来不知道的故事

早期版本虽然很不完善，但父亲是真正用过的。

因为当时使用 OpenClaw，我能在后台看到每一次对话，以及系统最后整理出来的总结。

聊过几次以后，很快就出现了一些质量不错的总结，而其中很多内容，是我以前完全不知道的。

这件事很重要，因为它第一次证明了这个产品不是“理论上有价值”。

即使只是一个很早期、很粗糙的版本，它已经开始让父亲讲出一些以前从来没有和我完整说过的事情。

而且父亲自己也有比较积极的使用意愿，并不是家人强迫他配合测试。

这也是后来愿意继续把这个项目做下去的一个重要原因。

#### 15. “7 天 10 万字”不是营销数字，是从真实使用量推出来的

“7 天从 0 到 10 万字”这个目标，并不是先想一个漂亮的宣传数字再往回解释。

它来自实际访谈量的推算。

设想的使用方式非常简单：

- 每天早晨采访半小时；
- 每天晚上采访半小时；
- 每天合计约 1 小时；
- 连续 7 天，大约就是 7 小时真实访谈。

按照真实语音访谈的信息量、转写量和后续整理后的文字规模估算，7 小时左右的访谈可以形成约 10 万字级别的回忆录素材与成稿基础。

所以这个目标本质上想解决的是传统回忆录最难的一件事：

> **不要让“写一本回忆录”变成一个持续半年甚至几年、最后大概率放弃的项目，而是把它压缩成普通家庭真正可能坚持完成的一周。**

#### 16. 为什么旧网页版必须被推翻

这次开发很大一部分痛苦，来自“人生采访局”其实不是从零开始，而是已经有过一个网页版。

问题是，旧网页版虽然能跑，但它本质上还不是一个真正的 Agent 系统。

当时更多是：

> 固定流程 + 固定模板 + 在指定节点调用大模型。

它缺少真正的 Agent Loop，也缺少 Agent 根据当前采访状态自主判断“下一步应该做什么”的能力。

而回忆录的业务逻辑却已经很复杂。

数据库里同时需要处理：

1. 用户长期背景；
2. 多轮原始对话；
3. 人生阶段与故事的树状结构；
4. 从访谈里抽取出来的事实；
5. 同一个事实在不同时间出现的冲突；
6. 后续新增的第三方故事补充；
7. 不同参与者之间的数据权限和安全边界。

当第三方补充故事加入以后，问题进一步复杂：谁说的、谁能看、不同人的描述冲突怎么办、第三方能不能看到主人公的私密内容，都开始变成必须解决的产品问题。

所以这次不是简单“给旧产品加几个 Agent 能力”，而是很多底层结构都需要重新理解和设计。

#### 17. 一开始，Summary 和 Agent Memory 其实被我们混在了一起

这是开发过程中一个很典型的认知变化。

最早的思路比较粗糙：

> 既然都是“对之前聊天的总结”，那 Summary 和 Memory 为什么不能是一个东西？

但真正做语音测试后，问题很快暴露出来。

给人看的 Summary，应该：

- 可读；
- 连贯；
- 像一段完整故事；
- 尽量减少技术痕迹。

而 Agent Memory 的目标完全不同。

它需要帮助模型快速判断：

- 这个人已经讲过什么；
- 哪些事实确认过；
- 哪些事情还有冲突；
- 哪些话题还没有深入；
- 下一轮最值得继续问什么。

如果强行把二者融合，就会出现两个问题：

1. 给人看的内容越来越像机器内部状态；
2. 给 Agent 用的内容又过于概括，缺少下一轮采访真正需要的结构化信息。

所以最后必须把它们拆开。

这是一个很典型的例子：**不是 AI 把代码写错了，而是一开始我们自己对产品的理解就不够深。**

#### 18. 快慢系统不是先设计出来的，而是被“重复提问”逼出来的

快慢系统也是这样出现的。

最开始我们以为，只要换一个足够强的实时语音模型，再给它一份 Summary，就能持续问出好问题。

实际测试不是这样。

即使语音模型本身已经很强，只要访谈越来越长，它能看到的上下文仍然有限。

于是就会出现：

- 问已经问过的问题；
- 忘记很久以前的重要事实；
- 明明历史里已经出现线索，却无法顺着继续追问；
- 下一问越来越泛化。

这些实际测试问题，最后同时推动了两件事：

1. 把 Summary 和 Agent Memory 分开；
2. 引入“慢系统”，让系统在实时对话之外主动回溯、搜索过去的聊天记录，把真正相关的历史内容重新送回实时采访链路。

所以慢系统不是为了“架构看起来更高级”，而是为了解决一个非常具体的问题：

> **一个实时语音模型，怎样在不背着整个几十万字历史上下文的情况下，仍然像一个真正长期采访过你的记者一样记得你。**

#### 19. 这个产品为什么天然涉及隐私

父亲自己对“回忆录应该怎么公开”的想法，也让隐私问题变得非常具体。

他的想法是最终至少保留两个版本：

**私人版**

给自己和家人留存，可以保留：

- 自己真实的观点；
- 对一些事情的判断；
- 对其他人的评价；
- 不适合公开的个人经历。

**公开版**

如果以后真正出版或者对外分享，就主动删掉这些涉及他人评价、家庭隐私和敏感关系的内容。

这让我越来越意识到，回忆录不是普通聊天数据。

一个人在这里可能会说出几十年来没有公开表达过的话。

因此，本地计算、权限隔离、不同版本输出、事实来源和敏感内容控制，并不是为了比赛增加技术点，而是产品本身天然要求这些能力。

这也是 DGX Spark 和本地 AI 对这个项目真正有价值的地方之一。

#### 20. 做家具营销反而提供了一部分最重要的产品能力

虽然不懂传统软件工程，但做家具营销并不是和这个项目完全无关的背景。

长期做营销和销售，一项很重要的能力就是：

> **听用户说了什么，同时判断他没有说出口的东西是什么。**

客户嘴上说“我再考虑一下”，真正顾虑的可能是价格、家人意见、空间尺寸，也可能只是还没有建立信任。

回忆录采访其实也非常类似。

一个人说“没什么可讲的”，不一定真的没故事；一个人忽然绕开一个问题，可能代表那里有情绪；一句很普通的话里，也可能藏着一个值得继续追问几十分钟的人生节点。

所以过去做家具营销形成的沟通、观察和需求洞察能力，后来反而成为产品设计里可以直接迁移的一部分。

#### 21. 太太在测试里承担的是“发现预期和现实不一致”

团队里另一个重要角色，是大量真实测试。

太太并不了解回忆录产品的历史设计，但这反而让她不会天然接受已有假设。

她在测试里做得最多的一件事，就是：

> 看系统真正表现出来的结果，和我们原本以为它会做到的事情，到底哪里不一样。

例如语音模型为什么没有问出有效的下一问、为什么开始重复、为什么某个流程在人实际使用时显得很奇怪。

这些测试反馈进一步推动了：

- Summary / Agent Memory 分离；
- 慢系统设计；
- 对语音模型真实能力边界的重新判断。

所以很多架构并不是纯粹坐在桌前设计出来的，而是被测试结果“逼”出来的。

#### 22. 如果最后没有得奖，这十天也完全值得

如果最后比赛没有拿奖，我并不会觉得这十天白做了。

第一，“人生采访局”本身只要真正好用，就已经有价值。

它以后可以给父亲、家人使用。

甚至我自己也准备开始写一份自己“前 1/3 人生”的回忆录。

很多事情现在觉得不会忘，但我已经越来越担心，如果一直不记录，等真正老的时候，大量细节可能早就消失了。

第二，这是我第一次真正借助 AI 做出来一个比较完整、像样的产品。

以前更多是在“使用 AI”。

这次开始真正碰到：

- 产品；
- 数据；
- 架构；
- Agent；
- Runtime；
- Memory；
- Retrieval；
- 实时语音；

- 测试与工程。

对 AI 的理解和对技术的理解都发生了非常大的变化。

单从这一点看，这十天的投入已经很划算。

#### 23. 2026-09-24：Step-Audio 2 mini 又让我们卡了很久

今天语音模型测试又遇到了一个很大的问题。

目前测试发现，Step-Audio 2 mini 在指令遵循方面比较弱。

对于普通实时聊天，它可以正常工作；但“人生采访局”的 System Prompt 和采访规则明显更复杂，需要它同时遵守：

- 采访目标；
- 追问规则；
- 不重复提问；
- 上下文约束；
- Tool Calling；
- 结束条件；
- 用户打断；
- 特定流程状态。

这些要求叠加以后，Step-Audio 2 mini 很容易开始偏离指令。

换到 Step-Audio 3 测试后，这类问题明显改善，因此目前初步判断不是整个产品 Prompt 设计完全错误，而是 mini 模型自身的能力边界已经碰到了。

但这件事还没有最终定论，现在仍然在继续测试。

这个问题已经消耗了相当长的调试时间。

它也很符合这十天的状态：

> **刚觉得语音链路已经接近完成，又发现底层模型能力本身可能不够，只能继续往下查。**

### 2026-09-25

#### 24. 差点放弃“纯本地”，又被慢系统救了回来

今天几乎一整天都在折腾实时语音模型。

问题还是同一个：本地可运行的实时语音模型，尤其是较小模型，在复杂指令遵循、长上下文理解和下一问质量上，明显不如云端更强的实时模型。

折腾到中间时，一度真的开始考虑：

> 要不要干脆放弃“尽量本地”的路线，直接用更强的线上实时模型算了？

因为如果最核心的采访体验做不好，本地部署本身没有意义。

但今天反复改了很多套方案之后，又出现了一个新的思路：

**不要强迫实时语音模型承担它并不擅长的全部工作，而是让慢系统承担更多“思考”和“记忆”的职责。**

实时语音模型继续负责它最擅长的部分：

- 听懂用户当前在说什么；
- 保持低延迟自然对话；
- 控制打断、轮次和基本采访节奏；
- 执行少量明确的 Tool Calling。

而慢系统可以在后台承担更多任务：

- 回溯过去多轮访谈；
- 判断当前回答和历史哪些内容真正相关；
- 补充 Agent Memory；
- 检查是否已经问过类似问题；
- 识别值得深入的线索；
- 给下一轮生成更明确的采访建议；
- 必要时把更完整的背景重新注入实时模型。

这样一来，实时模型不需要“脑子里一直装着整个回忆录”。

它只需要把眼前这一轮对话做好，而复杂的长期记忆和采访策略由慢系统在背后补上。

这其实是在重新理解“快系统 / 慢系统”的边界：

> **快系统不必足够聪明，它首先要足够快、足够自然；慢系统则负责把记忆、判断和采访策略补回来。**

今天最有意思的地方，是这个方案并不是一开始设计出来的。

而是经历了：

> 一个方案 → 测试不行 → 改；  
> 再一个方案 → 还是有问题 → 再改；  
> 一度准备放弃本地路线 → 再重新拆职责 → 又找到一条可能继续走本地的路。

目前这仍然只是一个正在推演和验证中的方案，还不能说已经证明成功。

但至少它让原本几乎准备放弃的“本地实时语音 + 本地智能系统”路线重新变得可行。

如果后面验证成功，这可能会成为整个项目里一个很重要的技术转折：

**不是靠换一个更大的模型解决所有问题，而是通过重新设计系统，让不同能力的模型各自只做自己擅长的事情。**

这也可能是 DGX Spark 这条路线真正有意义的地方：不是单纯证明“小模型也能代替大模型”，而是证明通过系统设计，本地较小模型依然可以参与完成一个原本看起来需要强云端模型才能承担的复杂任务。

## 四、潜在主叙事

目前最有力量的一条主线不是“我们用了多少 NVIDIA 技术”，而是：

> **过去，完成这样一个产品可能需要一个具备产品、前端、后端、数据库和 AI 工程能力的小团队；现在，一对在天津卖家具、没有传统软件开发背景的夫妻，也能够借助 AI，在真实问题中学习这些知识，并最终走进 DGX Spark Agent Skills 黑客松。**

这里不能写成“AI 已经让技术不重要”。

更准确的表达应该是：

> **AI 没有消灭技术门槛，但它显著降低了进入技术世界的前置门槛。过去要先学会很多东西，才有资格开始；现在可以先开始，然后被真实的问题逼着学习。**

“人生采访局”的整个开发过程，恰好可以作为这个变化的一个真实样本。
